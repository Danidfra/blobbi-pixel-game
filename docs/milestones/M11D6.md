## 3. Publishing architecture

```
IdentityScreen (consent: SHARE <name>)
  -> IdentityService.register(d)            identity.ts: backup checked (guest), owner may have a profile?
     -> activate()                          activation.ts: preflight, sign once, publish, read back
        -> Publisher                        publisher.ts: relayPublisher (Nostrify NRelay1) | memoryRelay (practice)
           relays + policy                  relay-config.ts: PUBLISH_RELAYS, REQUIRED_RELAY, policyMet, publishModeFor
  <- registered (live, confirmed): activatedAt, onRegistered (account adoption only if no other account)
  <- practiced (rehearsal): practicedAt, nothing else
```

- **Construction**: only `@blobbi-kit/core` (`buildEggTags` with `visualGeneration: 'v3'`, `updateBlobbiTags` to a
  Baby, `buildBlobbonautTags`/`updateBlobbonautTags`/`addPetToHas`, `getBlobbonautQueryDValues`,
  `isValidBlobbonautEvent`, `classifyBlobbiEvent` before publishing). No new kinds or tags, no explicit seed, d from
  the kit, look from (owner, d). `src/nostr/canonical-events.ts`.
- **Signing**: the vault (a guest identity) or the browser extension (an account). Every signed event is checked to be
  by the owner and to verify before it is stored. Only public, signed events are ever sent; the secret never leaves the
  vault (the boundary test enforces which modules may sign or send).
- **Ordering**: the Blobbi (31124) first; the profile (11125) only once the Blobbi is on at least one relay.
- **Idempotency**: the signed events are stored before anything is sent; every retry sends the same ids. A Blobbi
  already on the relays is adopted; a profile already listing it is left alone. Done is done (no second send).
- **Profile safety**: a profile is built from scratch only for a brand-new identity or when every relay answered.
  Just before the profile is sent the relays are asked again; a newer one made meanwhile is merged over (its Blobbis,
  content and other apps' tags kept). A legacy 31125 is carried into an 11125 with the canonical d.
- **Timeouts and disconnection**: each relay is opened for one request and closed; a request has an 8 s deadline;
  a relay that does not answer is just one that does not hold the event yet.
- **Rehearsal and live never mix**: runs are kept per mode; a live build ignores a rehearsal run and starts afresh.

## 4. Relay choices and the confirmation policy

Evidence (read-only inspection of the other apps, 2026-10-13; reachability by each relay's public NIP-11 page):

| Relay | Blobbi Standalone (`nostr-pet`) | Blobbi Island | Ditto (no relay list) | Answers | Pixel |
|---|---|---|---|---|---|
| relay.ditto.pub | reads, writes | reads | reads, writes | yes | publish, read, **required** |
| relay.primal.net | reads, writes | reads | writes only | yes | publish, read |
| relay.dreamith.to | no | no | reads, writes | yes | publish, read |
| relay.nostr.band | reads, writes | test only | no | **no** | dropped |
| relay.damus.io | no | no | writes only | yes | not used (no app reads it) |

`src/nostr/relay-config.ts` is the one place: `PUBLISH_RELAYS` = `READ_RELAYS` = ditto, primal, dreamith (MY BLOBBIS
reads from the same set, so what is published can be found by this game too). The kit has no relay constants.

**Policy** (`policyMet`): an event counts as shared only when a fresh query returns it (or a newer valid event by the
owner that still says the same) from **two relays, `relay.ditto.pub` among them** (the only relay every Blobbi app
reads). A relay's `OK` is recorded but is not enough; a WebSocket send with no `OK` counts for nothing; an `OK` false
with `duplicate:` means the relay holds it. Less than the policy but at least one relay holding both events is a
**partial** share: not registered, `TRY AGAIN` sends the same events only to the relays that do not return them.

**Live or rehearsal** (`publishModeFor`): REHEARSAL unless the BUILD sets `VITE_BLOBBI_PUBLISH=live`; on a development
server (`npm run dev`) `#publish=live` also works. A production build ignores the page flag.

## 6. Account and publishing UX

The flow keeps its order: the Blobbi and its worlds first, the backups, the check (mandatory before any publishing),
consent, and Nostr named only at the end. Changes:

- **Consent** says what sharing means, plainly: "Sharing makes {name} public: anyone in a connected world will be able
  to find {name}, its name, how it looks, that it is a Baby and that it belongs to this identity. Your island and your
  bag stay here, on this device." With another account connected: it stays connected, the Blobbi keeps its identity.
- **Practice is never told as sharing**: the practice run ends on PRACTICE COMPLETE ("nothing was sent. When it
  opens, you can share {name} from SETTINGS > ACCOUNT"); the Nostr reveal is kept for a real share. The working page
  says "Practicing: checking and signing. Nothing leaves this device."
- **Where it stands** (SETTINGS > ACCOUNT, one line and the row's label), `ShareStatus`: lives here (backup not
  checked), backup checked (not shared), practice done (nothing shared), sharing started, reached some worlds (try
  again), did not get through (nothing lost), shared. Partial and failed have their own words on the failed page.
- **The intro** goes straight to consent when the identity's backup is already checked (a restored identity).
- The two backups are unchanged (Recovery Key: simple, private, whoever has it controls the account; Protected Key:
  safer if found, a forgotten password cannot be recovered).

## 7. Restore UX (the reported bug)

After RESTORE the page shows the restored Blobbi itself (drawn from its canonical address, even with nothing walking),
"{name} is back! Your Blobbi is ready for another adventure. It is the same character: the same look and the same
name." and one primary action, CONTINUE WITH {name} (NOT NOW beside it).

- On the main menu, CONTINUE makes the restored Blobbi the chosen one (the player pressed it), then:
  - **islands saved**: the islands page, greeting it ("{name} is back! Choose an island, or begin a new adventure");
  - **no island**: straight into a new adventure (the Carrier, the name), where CONTINUE WITH {name} is offered first
    and MEET A NEW BLOBBI stays. Nothing is created until the player says so.
- While playing (restore from SETTINGS), CONTINUE brings it to this island, as before.
- A backup with no Blobbi named (a bare nsec): "Welcome back!" and CONTINUE returns to the menu.

PT-BR: "Momo voltou! Seu Blobbi está pronto para outra aventura." ES: "¡Momo volvió! Tu Blobbi está listo para otra
aventura." The restored Blobbi keeps its owner, d, look and Baby stage, and its name when the backup has it.

## 11. Security review

- **Keys**: generated in the vault (Web Crypto, AES-GCM, a non-extractable wrapping key in IndexedDB). Never in
  localStorage, a save, a URL, a log, analytics (there are none) or a network request: only signed public events are
  sent. Errors are problem codes; a relay's free text is reduced to its NIP-01 prefix.
- **Backups**: the Recovery Key only after the acknowledgment and a press, offered as a file, never drawn or copied;
  the Protected Key's password only on its page. Screenshots of every page show no key.
- **Debug utilities**: the `window.__blobbi` handle exists only on the development server (absent from the production
  bundle, checked). On a dev server it can reach the vault: never run a dev server with real identities.
- **CSP**: production `<meta>` CSP now allows WebSockets only to the three relays (`vite.config.ts`). A `<meta>` CSP
  cannot set `frame-ancestors`; hosting must send headers (beta checklist §12).
- **Limits** (unchanged, said plainly): any script that runs in the page can use the vault to sign or export; a
  browser extension with page access can read what the page reads; a plaintext Recovery Key file is the account.
