# M11D.8.4: The First-Load Inconsistency (Fix)

**Status: IMPLEMENTED, AWAITING MANUAL VALIDATION.** Branch `develop`, local commits only. Nothing pushed, deployed
or published; Ditto, Standalone and the kit untouched; no protocol change. The owner's browser storage was never read
or changed: everything below was found in the code and reproduced with a disposable key and stub relays.

Related: [M11D.8.3](M11D8-3.md) (the precedence rule this fixes the inputs of), [CURRENT-BLOBBI](../architecture/CURRENT-BLOBBI.md).

## 1. The report

Boca rosa walked the island Breezy Glade; Moon was set as companion in Ditto (kind 11125). The first load of Pixel
went straight in with Boca rosa. A refresh found Moon and asked "Who comes along?".

## 2. Root cause of the first load: one slow relay erased every answer

`resolveCurrentBlobbi` raced the reads against a deadline promise that, when the time ran out, aborted the reads AND
answered `null` in the same tick. The relay reader (`queryRelays`) waits for every relay (`Promise.allSettled`), so if
ONE relay had not answered by the deadline, the race was won by `null`: the profile read became "no relay answered"
(`unavailable`) even when the other relays had already returned Moon's profile. The entry treats `unavailable` as
offline and goes in with the device's Blobbi: Boca rosa.

Why the first load and not the second: on a cold page the deadline (4 s) also covered loading the network library
and opening six fresh TLS connections (three relays, two reads); the slowest relay (relay.dreamith.to, the slowest
in a live latency probe with a throwaway key: about 1.7 s warm from Node) can miss it. The refresh is warm (cached
library, faster handshakes), every relay answered, and Moon was found.

Evidence:
- At the previous commit, a reader that settles with two relays' answers on abort made the resolver return
  `unavailable` (probe, kept as the first test in `tests/m11d8-4-startup.test.ts`, which now expects `current`).
- In the real page with the real relay client, at the previous commit (temporary worktree of `0874df3`), with the
  stored state of the report restored before every load: all relays answering gave Moon on 4 of 4 loads; one relay
  that never answers gave **Boca rosa on 4 of 4 loads**. The same check on the fix gives Moon on 5 of 5 loads both
  ways (`scripts/m11d8-4-startup-browser.ts`).

Ruled out: the extension was ready (the island was entered, so `verifyExtension` answered with the account's key);
no stale cached result exists (every load reads afresh, nothing about the current Blobbi is stored); nothing applies a
remote choice after entry; no load writes a selection stamp (every write of the record is an explicit act or the
remote adoption, M11D.8.3 §3, pinned by tests). One more weakness was found and fixed: the read only began after the
extension check, so the two waits added up.

## 3. Why the refresh asked: the comparison branch

With Moon found and different from the walking Blobbi, "Who comes along?" appears only in the AMBIGUOUS branch:
no stamp on the device's choice, the two times within 60 s of each other, or one of them in the future (and no
remembered answer). A newer stamped local choice would have entered without asking; a newer remote one would have
brought Moon. The most likely branch for the report is **no local stamp**: Boca rosa's choice was stored before
M11D.8.3 (Breezy Glade with Boca rosa predates it), and an unstamped choice is never assumed old (M11D.8.3 §6). This
could not be confirmed against the owner's storage, which was not read; from now on every automatic entry writes a
diagnostic record that names the branch (§5), so the next manual run shows it.

## 4. The changes

| File | Change |
|---|---|
| `src/nostr/relays.ts` | `queryRelays` settles when every relay answered, when the caller aborts, or when a grace period after the first answer runs out, and ALWAYS returns what the answering relays sent (`reachable` counts them). The connection is injectable (`QueryOptions.open`) so tests drive this very code. The network library is still loaded once per request. |
| `src/nostr/current-blobbi.ts` | The deadline aborts the reads and then keeps their partial answers (`partial: true`); a reader that ignores the abort gets a 1 s backstop. |
| `src/playground/main.ts` | The current Blobbi (public data) is read from the start of the loading page, beside the extension's check, instead of after it; nothing is decided from it until the identity is confirmed. Deadline 6 s; once one relay answered the others get 1.5 s. The facts carry the existed-by bound (§5) and every automatic entry writes the diagnostic record. |
| `src/game/blobbi-selection.ts` | `noteUnstampedChoice`: an UNSTAMPED choice gets, once, `existedBy` = the moment this code first saw it (an upper bound on its time, never its time); answering the question drops it. Stamped records are never touched. |
| `src/game/world-entry.ts` | `selectionOrder` (with the reason and the basis) behind `compareSelections`: a stamp orders both ways; an existed-by bound can only find the local choice OLDER (a remote choice more than 60 s after it); nothing else about an unstamped choice is assumed. `entryDiagnostic` and `ENTRY_DIAGNOSTIC_KEY`. |

## 5. The diagnostic record

`blobbi-pixel-lab:entry-diagnostic` (this device only, never sent): the decision, the title reason, the current
Blobbi's status and whether the read was partial, whether the two choices differ, the order and the ambiguity reason
(`no-local-time`, `no-remote-time`, `future`, `too-close`, `no-clock`), how the local choice is known
(`stamp-player`, `stamp-remote`, `bound`, `none`, `no-record`), the gap in seconds, whether a remembered answer
applied, and how long the entry waited. No key, no address, no name (tested). To read it after a manual load:
DevTools > Application > Local Storage, that key.

## 6. Why it is deterministic now

The outcome depends on the stored state and on what the relays hold, no longer on which relay is slowest: whatever
arrives before the deadline (or the grace) is used, and a missing relay only marks the answer `partial`. Repeated
loads from the same stored state with all relays, with one relay hanging, and with an unstamped choice give the same
outcome on every load (browser check: 5 loads each). The only writes on load are the one-time `existedBy` (once per
unstamped record, never moved) and the diagnostic record; neither is a selection.

2. Reload several times, hard and normal: the same outcome every time, no question.
3. In Ditto, set Moon (or the other one) again: reload: it comes along without a question.
4. In MY BLOBBIS, BRING the other one; reload: it stays.
5. Throttle the network (DevTools, Slow 3G): the same outcomes, after a longer loading page.
6. Network off: the device's Blobbi after about 7 s, no question.

## 10. Limitations

- An unstamped choice and a remote choice made BEFORE this code first saw it still cannot be ordered: the question is
  asked once (the report's refresh). Making it automatic would mean assuming the old choice is older, which the
  brief forbids.
- The wait is longer when relays hang: the read has 6 s (was 4 s); offline entry measured 7.8 s in the browser check
  (was 5.7 s). A relay that does answer costs at most 1.5 s more than the first one.
- `partial` answers can miss a newer profile held only by the relay that did not answer: the older one is used for
  that load; the next load with that relay answering corrects it.
- Offline, an island whose last visitor is an account Blobbi this device cannot name without the relays (not the
  stored choice, not a Blobbi met here) is not recognised as the player's: the title shows (unchanged from M11D.8).
