## 1. The missing egg (investigated first, FIXED)

**Reproduced in headless Chrome**: pressing Enter twice on CREATE ISLAND (150 ms apart). The intro cinematic starts a
frame or two after the first press, so the second press landed on it as "skip": the whole intro was skipped at 0.0 s,
the birth was counted as seen (`born: true`) and the egg never showed, then or later. A single press played it
normally (birth true, egg shown). Mouse and tap skips had the same hazard.

**Fix**: `IntroCinematic.requestSkip()` ignores a player's skip (a key, a click, a tap) for the first `SKIP_GRACE`
(1.5 s) of the cinematic; the "any key or tap: skip" hint appears only after it. After the fix, the same double press
keeps the birth playing (verified in the browser). Tests: `tests/m11d4.test.ts` (the grace) and the browser run.
Other suspects audited and ruled out: the New Adventure flow, companion reuse (a kept Blobbi has no egg by design),
intro eligibility (`unbornHere`), reduced motion (the egg shows, briefly), save and resume (the birth replays after a
reload until seen).

## 2. Architecture

| Layer | What | Where |
|---|---|---|
| Key vault | the ONLY holder of secret keys: makes keypairs (nostr-tools `generateSecretKey`), seals them (AES-GCM under a non-extractable Web Crypto key, pubkey as associated data), signs (`finalizeEvent`), makes and opens NIP-49 backups (nostr-tools `nip49`) | `src/nostr/keystore.ts` (IndexedDB `blobbi-pixel-vault`; memory backend for tests) |
| Reserved Blobbis | public records: owner, owner kind, petId, the kit's canonical d, name, birth, island met on, born, registered | `src/game/guest-blobbis.ts` (`blobbi-pixel-lab:guest-blobbis`) |
| Canonical events | the hatched Baby's 31124 and the owner's 11125, from `@blobbi-kit/core` only | `src/nostr/canonical-events.ts` |
| Backup file | readable text, the NIP-49 `ncryptsec`, a public line naming the Blobbis | `src/nostr/backup.ts` |
| Registration | consent, a verified backup, preflight, sign, publish, confirm; resumable and idempotent | `src/nostr/activation.ts` (`blobbi-pixel-lab:activation`) |
| Publishing | the only module that sends events: real relays or the in-browser rehearsal relay | `src/nostr/publisher.ts` |
| Service and port | ties them together; the UI sees only public data and finished files | `src/nostr/identity.ts`, `IdentityPort` in `src/nostr/port.ts` |
| Account flow | the in-game screens | `src/ui/screens/identity.ts`; entries in SETTINGS > ACCOUNT and the title's LOGIN WITH NOSTR |
| Boundaries | secrets only in the vault, signing only in the vault and the extension signer, sending only in the publisher; nothing secret in localStorage; comments excluded | `tests/boundaries.test.ts` |

Identity, Blobbi and island stay separate records: an identity may own several Blobbis (a registered guest identity
becomes the player's account and owns the next Blobbi met too), a Blobbi may visit any island, an island never names a
Blobbi or an identity (island saves are byte-identical around a registration, tested).

## 3. Threat model (what is protected, and what is not)

| Threat | Protected? | How |
|---|---|---|
| Someone reads localStorage, a copied browser profile, a disk backup | **Yes** | no secret is ever in localStorage; the vault records are ciphertext; the wrapping key is a non-extractable CryptoKey whose bytes no script can read or export |
| Another website | **Yes** | same-origin storage |
| A record swapped onto another identity | **Yes** | the pubkey is the AES-GCM associated data; the decrypted key is checked against its pubkey |
| A script running IN this page (an XSS, a compromised dependency, a malicious extension with page access) | **No** | it can ask the browser to decrypt with the wrapping key, as the game itself does. The CSP (below) narrows how such a script could get in; it does not make keys safe from one that does |
| The player clears site data, or Safari evicts storage after 7 days without a visit | **No** (keys are lost) | the verified NIP-49 backup is the recovery; the flow says so in plain words before anything is promised; `navigator.storage.persist()` is asked (best effort) |
| A lost or forgotten backup password | **No** | said plainly: nobody, not even us, can open it |
| A started download that never saved | **Covered** | a backup counts only after it was loaded back (file or pasted text) and opened with its password |
| Publishing by accident | **Covered** | nothing is signed or sent before SHARE; a guest also needs a verified backup; live publishing is off in this build |

**Content Security Policy** (production build, a `<meta>` added by `vite.config.ts`): `default-src 'self'; script-src
'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self' data:; connect-src 'self' wss:;
worker-src 'self' blob:; object-src 'none'; base-uri 'none'; form-action 'none'`. Checked in the browser on the
production build: a new adventure (the lazy crypto chunks, the vault, the birth) ran with no violation; the only console
error was the missing favicon. A hosting header can add `frame-ancestors 'none'` (a meta tag cannot).

**Plaintext lifetime**: a secret is decrypted only inside the vault for one operation and zeroed right after; the UI
never receives one; passwords and loaded backups live only on their page of the flow and are cleared on every page
change; the hidden input that receives typed text is emptied on blur.

**Cross-app note**: the Blobbi Standalone (`nostr-pet`, read only) currently keeps its guest key as a plain nsec in
localStorage (`blobbi:guest:v1`); its own SECURITY.md proposes this same sealed design (not built there yet). Backups
are interoperable: both use NIP-49 `ncryptsec` and the file name `blobbi-nostr-key-backup-<npub8>.ncryptsec.txt`.

## 4. A new Blobbi's identity (IMPLEMENTED)

NEW ADVENTURE, meeting a new Blobbi:

1. **Whose?** As a guest: a new identity of its own. Connected (M11D.4 title page "Whose Blobbi will it be?"): ON MY
   ACCOUNT (an extension account: no key is made; an identity this game keeps: that identity) or ITS OWN IDENTITY, HERE.
   Never decided silently; no ownership transfer is offered.
2. A guest identity is made and **sealed in the vault first**; only a kept identity gets a Blobbi (a vault that cannot
   keep it makes nothing and says so: "This browser could not keep the new Blobbi's identity safely, so no island was
   made").
3. `petId` = the kit's `generatePetId10`, d = the kit's `getCanonicalBlobbiD(owner, petId)`: the V3 look is the kit's
   `deriveBlobbiV3Seed(owner, d)` from this moment, for the egg and the Baby alike, and on every app once registered.
4. The island is made, the Blobbi chosen (selection record `guest: true`: it walks with or without an account), its
   egg hatches (the M11D.3 birth), `born` is set when the birth is seen or skipped. Nothing is signed or published.

## 6. Backup and restore (IMPLEMENTED)

- **File** `blobbi-nostr-key-backup-<npub8>.ncryptsec.txt`: a few lines in the player's language (what it is, that it
  opens only with the password, how to bring the Blobbi back), the NIP-49 `ncryptsec` (scrypt logN 16, key-security
  byte 0x02 "unknown"), and `blobbi-pixel-backup v1 {pubkey, blobbis: [{d, petId, name, bornAt}]}` (public facts).
- **Verification** = the file (or its text) loaded back and opened with the password, and its key equal to the
  identity; recorded in the vault (`backupVerifiedAt`).
- **Restore**: parse (one ncryptsec, at most 16 KB), open (wrong password vs damaged told apart), preview the identity
  and the Blobbis its public line names (the line counts only if it names the very identity the backup opens), then
  restore: an identity already here is never overwritten or duplicated, a Blobbi already here is left as it is,
  nothing is published, no island changes. A restored identity is marked backup-verified.

## 7. Registration and Nostr events (IMPLEMENTED; resumable, idempotent)

- **31124**: `buildEggTags(owner, petId, bornAt, name, { visualGeneration: 'v3' })` then `updateBlobbiTags(…, { stage:
  'baby', state: 'active', progression_state: 'none' })`: the kit's canonical d, the ecosystem marker, stats at the
  maximum, `visual_generation=v3`, no seed and no trait tags. The kit reads it as a modern canonical Baby whose seed is
  `deriveBlobbiV3Seed(owner, d)` (tested): the same look in every app. Not given the kit's evolve missions (they live
  in `@blobbi-kit/react`, not part of this game; inventing them would change the protocol): `progression_state: 'none'`
  lets the Blobbi's home apps start its growth their own way (decision 2).
- **11125**: `buildBlobbonautTags(owner)` (or the newest existing profile) with `has` += this d (`addPetToHas`) and
  `current_companion` = this d; never dropping a Blobbi it already lists.
- **Steps**: preflight (the Blobbi by `#d`, the profile by author; a Blobbi already there is ADOPTED, never re-created;
  a profile already listing it is left alone) → sign (the vault, or the extension for an account Blobbi; a signer that
  answers as someone else is refused) → the SIGNED events stored before sending → publish the Blobbi, then the profile
  (a step no relay accepted stops the run) → confirm by reading both back → the identity becomes the player's account
  (`method: 'vault'`), the Blobbi `activatedAt`. Every retry sends the very same events (same ids): no duplicates.
- **No departure or arrival**: registration never touches the Blobbi in play or the island (tested: same Blobbi, same
  spot, present, no swap; island save byte-identical).

## 8. Publishing mode (DECISION FOR THE OWNER)

This build publishes in **REHEARSAL** mode: an in-browser relay (`memoryRelay`) receives the events, gives them back
for confirmation, and nothing leaves the device; the UI says "Practice mode" on the consent and reveal pages. Real
relays (`wss://relay.ditto.pub`, `wss://relay.primal.net`, `wss://relay.nostr.band`, the Standalone's set) are used only
when the page is opened with `#publish=live`. Live publishing was never run during development.

## 9. Existing accounts (IMPLEMENTED)

LOGIN WITH NOSTR (the existing NIP-07 connection) offers CONTINUE WITH ONE OF MY BLOBBIS (MY BLOBBIS: eligible
Blobbis, explicit choice, the V1/V2 world-form consent, the canonical stage, the arrival animation, never a birth) and
MEET A NEW BLOBBI (the deliberate new-Blobbi flow, with "Whose Blobbi will it be?"). A Blobbi on an extension account is
registered with the extension's own signature (it shows its prompt), after the same consent; no backup step (the
account is the player's own). Existing canonical eggs are never hatched here.

## 10. Legacy local Blobbis (M11D.3)

Kept exactly as they were (`blobbi-pixel-lab:local-blobbis`, never rewritten or deleted); they still walk and can be
kept in a new adventure. They have no reserved identity, so they cannot be registered with their look, and the flow
says so kindly ("A Blobbi from the very first days ... It stays here with you, just as it is, but it cannot travel to
other worlds. A Blobbi you meet in a new adventure from now on can."). No migration is offered: canonical rules cannot
keep their look.

## 11. Failure recovery

| Interrupted during | Outcome |
|---|---|
| key generation / sealing | nothing is handed out until the sealed record is read back; no Blobbi is made |
| egg creation (island making fails) | the unborn Blobbi record is forgotten; its sealed key stays (never deleted) |
| backup creation | nothing stored; make it again |
| backup verification | not verified until it opens; retry any time |
| signing | the run stays at consent; nothing sent |
| publication (none or partial) | the signed events are stored; TRY AGAIN sends the same ones (only what was not accepted) |
| confirmation | stays `published`; TRY AGAIN reads back again |
| before local cleanup | the Blobbi is marked registered only after confirmation; records are never deleted |
| restoration | inspecting stores nothing; a restore either stores the identity or not; Blobbis already here are never duplicated |
| a second tab upgrading the vault | connections close themselves on `versionchange`; a vault database missing its stores is completed (only adding) |

## 12. Save protection

Island saves unchanged (schema 12), never naming a Blobbi or an identity; registration and restore never write one.
New per-browser records: `blobbi-pixel-lab:guest-blobbis`, `blobbi-pixel-lab:activation` (both public data), and the
IndexedDB vault `blobbi-pixel-vault`. The account record gains `method: 'vault'`. Deleting an island never touches an
identity, a key or a Blobbi.

## 13. Known limitations

- **KI-90** Live publishing is off (rehearsal) until the owner approves it (`#publish=live` for a deliberate test).
- **KI-91** Keys in the page can be used by any script running in it (threat model); the CSP is a meta tag (no
  `frame-ancestors`) and the dev server has none.
- **KI-92** Registered Blobbis carry no evolve missions (`progression_state: 'none'`).
- **KI-93** Account-owned Blobbis need the extension to sign (no remote signers, NIP-46, yet).
- **KI-94** A restored Blobbi is restored as a guest Blobbi; if it was registered before, a new registration adopts it
  from the relays (live mode) without publishing again.
- **KI-95** Typing goes through a hidden input: on touch devices the keyboard must appear when a field button is
  pressed (not verified on a phone).
- **KI-96** Rehearsal mode keeps its relay in memory: after a reload a rehearsal registration re-runs from its stored
  signed events (same ids).
