### Signer connection, verified (NIP-07)

Read in source (`src/nostr/account.ts`, `src/nostr/signer.ts`, Nostrify 0.55.1 `NBrowserSigner.ts`):

- The public key comes **only** from the extension: CONNECT and CHECK THE ACCOUNT AGAIN call
  `window.nostr.getPublicKey()` through `NBrowserSigner` (which waits up to 1.5 s for a late-injected extension and
  rejects a non-string). The answer must be 64 hex characters and a valid secp256k1 x coordinate
  (`isPublicKeyHex`), else "invalid-key" and nothing changes.
- The npub on screen is `npubEncode(pubkey)` of that exact key; the profile name is read only for that key, from
  kind 0 events **by that author** (`parseProfile` rejects others).
- The game's signer interface has one method, `getPublicKey`; the boundary test forbids `signEvent`, `nip44`, `nip04`,
  secret-key APIs and `.event(` everywhere, `src/nostr/` included. The account record holds public data only.
- **No prompt in Brave is plausible**: NIP-07 leaves permission UI to the extension; many grant `getPublicKey`
  without a dialog or remember the site (Brave's wallet, nos2x, Alby and others differ). The game adds no prompt of
  its own (none is needed for a read-only public key).
- Reconnection: the same key keeps its cached profile; another key starts fresh, cancels any profile or Blobbi read
  for the old one (late answers are dropped) and makes a Blobbi chosen with the old account stop walking.

**Verifying the npub by hand.** ACCOUNT → ADVANCED DETAILS shows the npub on two lines (32 + 31 characters) and the
hex key on two lines. In the extension (Brave: the wallet / Nostr panel; Alby: account settings; nos2x: options),
copy the account's npub (or public key in hex) and compare **every character**, not only the short form. Then
press CHECK THE ACCOUNT AGAIN after switching accounts in the extension: the npub must change to the new one.

## Phase 2: MY BLOBBIS (read-only canonical Blobbi discovery)

**Where.** SETTINGS → ACCOUNT → MY BLOBBIS (the first button when connected). No new key (every letter is taken).

**Reading.** `NostrAccount.loadBlobbis()` asks the two Blobbi relays (`wss://relay.ditto.pub`,
`wss://relay.primal.net`) with one REQ each, `{kinds:[31124], authors:[pubkey], "#b":["blobbi:ecosystem:v1"],
limit:200}`, each relay opened for it and closed after; `NRelay1` verifies signatures. Only when the screen opens
(or TRY AGAIN / SEARCH AGAIN); cached in memory for 5 minutes per account; 8 s deadline; never in the game loop,
never blocking play (the world is paused only because a menu is open, as for every menu).

**Checking** (`src/nostr/blobbis.ts`, `pickBlobbis`), with the kit's own rules (`@blobbi-kit/core` 0.9.0):

| Check | Rule |
|---|---|
| Author | `event.pubkey` must equal the connected key (a relay ignoring `authors` cannot slip one in; the kit's readers do not re-check this, M11A). |
| Structure | NIP-01 shape (`isWellFormedEvent`), kind 31124, a `d` tag. |
| Duplicates / relays disagreeing | Per `d`, the newest `created_at` wins (ties to the lower id), whichever relay sent it; the same event from two relays counts once. |
| Validity | the newest event must be `classifyBlobbiEvent(e) === 'modern'` (ecosystem marker, known stage and state, `last_interaction`, canonical `d`, name, seed); legacy and invalid ones are skipped, never repaired. If the newest is malformed, the Blobbi is not shown (no fallback to an older state), as the kit's collection does. |
| Generation | `visual_generation` read raw: absent V1, `v2`, `v3`, anything else **unknown** (the kit would read it as V1 and drop it as legacy; listed instead when schema-valid and canonical). |
| V3 identity | seed = `deriveBlobbiV3Seed(owner, d)`; must equal the kit's `v3Identity.seed`. Choosing re-resolves the address through `resolveBlobbi` and refuses any mismatch. |
| Names | cleaned like profile names (no control/direction/invisible characters, 24 characters). |
| Failures | no relay answered → "unavailable" (TRY AGAIN); one relay down → "One relay did not answer."; a count of unreadable events is shown in small text. |

**What may visit.** Only a **V3 adult**: the pixel game draws the V3 adult form gene for gene (the same sprite that
walks). V1/V2 (other art, another seed), V3 eggs and babies (other bodies; the pixel rig is adult only, KI-69) and
unknown generations are listed with the reason and **their real colours only** (V1/V2 from the kit's trait reading,
a V3 egg or baby from its V3 genome) and the line "Only its colours are shown here, not its picture." Nothing is
drawn as something it is not.

**Choosing.** "Bring to the island" → the Blobbi walks the island; its name shows on the status card; "Walking with
you" and a green mark show the current one; "Use the visiting Blobbi" goes back to the demo Blobbi (`blobbi-9`).
Nothing is created when the list is empty ("No Blobbis were found for this account. Blobbis are adopted in other
Blobbi apps..."), and the player is never sent anywhere.

**Persistence (no schema change).** The choice uses the existing per-browser record
`blobbi-pixel-lab:selected-blobbi` (`{version: 1, source}`, a `v3-address` as since M3.4) with two optional fields:
`name` (presentation) and `account` (the key it was chosen with, which must own the address). Older code reads only
`version` and `source`, so the record stays compatible both ways. **No island save changes**: saves never name a
Blobbi (`owner: 'local-world'`); the test re-saves an island after choosing and finds the bytes free of the address
and the schema at 12. Guest worlds, the demo companion, world generation, quests, the Carrier, island objects, the
bag and save recovery are untouched. A Blobbi chosen with an account walks **only while that account is connected
on this device** (`effectiveSelection`): disconnecting or switching brings the visiting Blobbi back without erasing
the choice, and reconnecting the same account restores it (also at start-up, also for a link naming it).

**No publishing.** The fake relay in the screenshots recorded only `REQ` and `CLOSE` frames from the game; the mocked
extension was asked nothing (the key was remembered). Unit tests: the real relay reader against a mocked `NRelay1`
sends no event and closes every relay; the extension is asked only `getPublicKey`.

## Generation compatibility (V1/V2), investigated again

Finding (read in the renderer 0.6.0 types): `generateGenome` accepts an explicit **semantic identity** (colours,
pattern, mark, antenna, horns, ears, tail, belly, freckles) besides the seed, and `canonicalGenome()` is "tuned
against the current Adult V2 drawing". So a deterministic, recognisable **local world form** is technically within
reach: the V2 body is close to the canonical V3 morphology, and V1/V2 colours and pattern vocabulary map directly.
It was **not shipped** in M11C, because the M11B prerequisites still hold (the owner and the kit maintainer agree on
the mapping and its wording; the original V1/V2 art shown alongside; test vectors; no write path). The concrete
plan is in [Blobbi generations](../architecture/BLOBBI-GENERATION-COMPATIBILITY.md) §5.

## Performance

- HUD cost, measured back to back (node, `tsx`, 1280×720, view + UI layer, best of 5×120 frames): desktop 1.521 ms
  without the chip and hotbar, **1.537 ms** with the chip and a five-slot hotbar; touch 1.541 → **1.574 ms**. The
  hotbar card is cached until the bag, the hand, the scale or the language changes; the chip is cached text.
- Identity status is updated by account change events (no per-frame `snapshot()`/bech32 work).
- Relays: at most one read per account per 5 minutes unless the player asks; no network in the game loop.
- Bundle: main JS 884.58 kB (305.14 kB gzip) at M11B → **909.05 kB (313.79 kB gzip)**: the hotbar, MY BLOBBIS and
  the kit's Blobbi event parsing (statically imported by the account; the network library itself stays in the lazy
  226.08 kB Nostrify chunk, fetched only on connect or a read).
